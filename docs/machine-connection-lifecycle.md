# machine_connection 记录的生命周期与四层防护

> 写于 2026-08-07，起因是 `fix/ddn-reconnect-ownership-2026-07-28` 并入 main 时与 `f23d794` 撞车。
> 两边看着像"同一个 bug 的两套修法"，实际是**冲着两个不同故障去的**，都必须留着。
> 下次再看到这两套机制并存时，先读这篇，别把任何一层当成冗余删掉。

## 背景：这条记录为什么危险

机器 WS 连上 DDN 时往 MongoDB `machine_connection` 插一条记录，`IsMachineConnected` 据此判重复连接。
这条记录一旦**该删没删**，机器就再也连不上 DDN → 链上 `dbcAI online=false` → 不可租，
而且检测节点会判它离线 → 触发 `offline_slash` **罚款**。所以这里的每个洞都是要花钱的。

## 故障 A：DDN 进程重启/崩溃 → 全部在连机器一次性孤儿化

`readPump` goroutine 被直接终止时断开清理不执行，**当时所有在连机器的记录全部留下**。
更糟的是被拒的重连 `MachineKey` 为空、它的断开也不清理 → 孤儿永不消失。
**实测：6-17 换 IP（=进程重启）留下 303 条孤儿，卡了 3 周。**

### 第 1 层 · 启动清理（`f23d794`，2026-07-08）
`hub.InitHub` → `db.ClearAllMachineConnections`：进程刚起、尚无任何活连接，
**此刻集合里的每一条按定义都是上周期的孤儿** → 整表清空，权威对账。清理失败只告警不阻断启动。

### 第 2 层 · 孤儿回收器（`8de1806`，2026-07-28）
`runOrphanConnReaper`，**每 2 分钟**一轮：清理"内存所有权登记里已无活所有者"的记录。
覆盖进程**运行期间**产生的孤儿（异常断开且清理失败、掉电等），这是启动清理够不到的。

> 第 1 层与第 2 层**互补，不是重复**：一个是开机瞬间的权威对账，一个是运行期的持续兜底。
> 只有第 2 层时，进程重启后孤儿要等最多 2 分钟才消失；只有第 1 层时，运行期产生的孤儿要等下次重启。

## 故障 B：机器硬重启/掉电 → 旧连接还"活着"，新连接被拒

机器突然断电重连时，旧的那条 TCP 连接不会立刻消失，要等读超时（`pongWait` 30s）。
这段时间里"本实例内存中确实有一条活连接"是**真的**，于是任何基于
"有活连接就判重复连接并拒绝"的逻辑都会**把正当的重连挡在门外**。

### 第 3 层 · 所有权接管（`8de1806`）
入口**不再拒绝**。等所有校验都过了（`GetMachineState` / 注册 / 上链 `Report`）之后才
`hub.becomeOwner`：原子地把所有者切成新连接，旧连接标 `superseded` 并 `Close()`。
放在校验之后是刻意的 —— 否则新连接校验失败会白白把旧连接踢掉、机器直接掉出 DDN。

### 第 4 层 · 连接感知的断开清理（`8de1806`）
`releaseOwner(machine, c)` 判定"我是否仍是当前所有者"：
- 是 → 正常删记录 + 排下线
- 不是（已被顶替）→ **不删记录、不排下线**

这一层堵的是一个**会花钱的洞**：旧连接晚几十秒才超时退出，那时记录已经是新连接写的了；
没有这层判定，旧连接的清理会删掉**新连接的**记录 → 新连接被当成没连上 → 误判离线 → 罚款。
配套：`MachineConnected(ctx, key, c.ClientID)` 写入 `conn_id`，供退出时做连接感知删除；
集合也补上了 TTL（`SetExpireAfterSeconds`）作最后兜底。

## 为什么 `f23d794` 的"重连自愈"那一段可以合掉

`f23d794` 除了第 1 层，还有一段"记录已存在但本实例无活连接 → 删掉放行"的即时自愈。
合并时保留了分支侧、丢掉了这一段，理由：
- 它只在"**没有**活连接"时放行，"**有**活连接"时仍然 `return "repeated connection"` 拒绝
  → **故障 B 这个最典型的场景它恰好盖不住**；
- 它想解决的"记录残留导致连不上"，在分支的模型里从根上不存在：**入口根本不拒绝**，
  `MachineConnected` 的 upsert 直接覆盖旧记录；孤儿本身还有第 1、2 层收。

因此 `hub.hasLiveConnection()` 目前**没有调用方**（保留未删）。
它与 `isMachineOwned()` 语义相近但不等价：前者查 `wsConns`，后者查所有权登记 `machineOwner`。
**要用请用 `isMachineOwned()`**，下线复核等判定都以所有权登记为准。

## ⚠️ 单实例硬约束

第 2/3/4 层的判定**全部基于本进程内存**（`machineOwner`）。`InitHub` 启动时会打一条 Warn 说明这点。
**多个 DDN 实例连同一个 MongoDB 会出人命**：一个节点会把"连在另一个节点上的机器"判成无所有者，
于是清掉它的记录、并**上链报离线** → 误罚。要上多节点必须先引入节点级所有权（记录里带 node_id，
清理/下线只对自己 node_id 的记录生效）。当前生产是单实例（47.130.164.32 单进程）。

## 教训

1. **"两套修法撞车"要先问"它们各自冲着什么故障"**，而不是"哪套更新/哪套在线上跑"。
   本例里两边解决的是完全不同的两个故障，任何"二选一"都会丢东西。
2. **别用"当前二进制里没有这个字符串"推出"这个修复从未部署过"** —— 只能推出"现在没有"。
   要判断是否部署过，看提交信息/部署记录/更早的构建。
3. **长期存在的特性分支会静默回滚主干上的修复**：分支切出去之后主干合入的东西，
   分支构建一部署就全没了。分支活得越久越危险。
